# Task responsibility and history checkpoint

Source: workflow §§12, 22 and 26; package §3.7 (core tasks) and §4.3 (advanced tasks). This extends the existing task/request mutations and shared drawers. It does not replace the working task, request, housekeeping or maintenance modules.

## Delivered

- Actual assignment time for newly assigned/reassigned tasks, generated by a database clock. Direct creation, recurring task creation and guest-request conversion use the same rule. Existing assignment dates remain unknown; migration does not fabricate old lifecycle events. Current completion duration is measured from task creation to completion; overdue duration uses the due date and completion time, or now for open work. Cancelled work does not keep accruing overdue time.
- Database-generated, append-only task history records before/after state, actual occurrence time, actor where known, assignment/department labels, links, priority, due dates and lifecycle timestamps. Old labels and the previous assignment's accepted/started/completed times remain in history after reassignment or later staff/department renaming. Task descriptions, comments and attachments are not copied into the history snapshots.
- Direct vehicle and maintenance-ticket links have composite tenant foreign keys. Linking requires the relevant module read grant and feature, including maintenance department/own-record scope. Conflicting vehicle/room references are refused. Explicit null patches can clear the new links. Saved historical vehicle/ticket labels are disclosed only under current module and record access.
- Reads use current task visibility: department managers see their department and assigned staff see their own tasks. History is part of the existing Task capability, not a separately charged feature. Direct task, checklist, comment and attachment URLs now also enforce the Task capability. A disabled feature cannot be used through these routes.
- History insertions only originate from a task trigger. FORCE RLS and application-role grants protect tenant scope; UPDATE/DELETE are revoked and append-only triggers remain in force. There is no history write/delete API or new RLS bypass. Historical task IDs are evidence references rather than cascading live-record dependencies: an authorised database deletion can retain the evidence, while task/history and existing AI source readers refuse the deleted resource.
- Normal task updates and confirmed AI updates share deterministic record locking with guest-request resolution. Repeated/concurrent completion cannot create another recurring task. Mutation queries avoid intermediate autoflush history entries. Locked reference queries refresh cached ORM rows before validation, including staff changes committed while an edit or AI confirmation is waiting. Existing required-checklist/proof and status-transition rules remain authoritative; failed operations roll back history too.
- Recurrence keeps permitted links and existing checklist/proof behavior. Recurring and request-converted task assignments enqueue the same assignment notification as direct tasks. Inactive or department-incompatible staff are not copied into a new recurring assignment. Disabling advanced tasks stops new recurrence creation while allowing the existing task to be completed; enabling a feature later does not backfill that completed chain.
- AI link removal appears explicitly in its proposal/review and remains subject to the existing one-time confirmation. Proposal preparation/review rolls back the history generated by dry runs. The expanded tool schemas still fit the existing conservative context budget after removing repeated wording; the budget, server authorization and confirmation checks were not relaxed.
- The task drawer shows known/unknown lifecycle times, total completion/overdue duration and a paginated history. Managers can reassign and change permitted links. Directory lookups and edit controls require their independent grants/features; read-only accounts do not request forbidden lookups. Account/lodge changes discard previous content and late responses. UI copy is centralised for future translation, with both shared themes and inline feedback preserved.

## Upgrade and verification

Back up first, upgrade through `0024_task_history`, run the existing app-role grants step and rebuild API/web services through the normal Compose workflow. API/workers retain NOSUPERUSER/NOBYPASSRLS. No customer volumes need to be removed. Downgrade removes the new task-history table, links and assignment timestamp; export/back up that evidence first. The rehearsal used a disposable database and preserved existing task descriptions, original creation dates and assignment uncertainty across upgrade/downgrade/re-upgrade.

Validation: **745 API tests pass**, including **20 dedicated task-history cases** and the existing confirmed-action, RLS, CSRF, MFA, package, audit and deleted-source suites. The combined focused task/action suite passes 47 checks. Independent-manager completion/request-resolution races and staff changes committed while a lock is waiting are exercised against real PostgreSQL. The production frontend build and **all 46 browser checks pass**. Task drawers pass both themes at 375/768/1366/1440 px, with no horizontal overflow or automated WCAG A/AA violations; read-only views avoid forbidden lookups and discard late history after a lodge change. Migration roundtrip, static guard audit (168 main routes, zero issues), Compose configuration and diff checks pass.

Review fixtures: [desktop task history](screenshots/safarios-task-history-desktop-dark.png), [mobile task history](screenshots/safarios-task-history-mobile-light.png). Scripted browser fixtures validate interaction and layout; they do not establish actual email delivery, production load, comprehensive accessibility certification or full commercial acceptance. No customer database was migrated or production environment deployed.

## Still open

Advanced task templates, configurable escalation/automation, broader reporting/export and the complete connected guest/front-office/department acceptance journeys remain. Permanent memory for every other module still needs its own relationship/history acceptance. The existing AI history reader still uses its original allowlisted operational events; exposing the new task snapshots to AI needs a separately scoped reader and privacy/grounding tests. This checkpoint does not claim that AI already answers every historical assignment question. The guest web/QR portal, documented offline subset, live integrations and production acceptance remain in the [document-led register](REQUIREMENTS_DELIVERY.md). Native apps, payroll and payment processing remain outside the agreed initial web scope.
